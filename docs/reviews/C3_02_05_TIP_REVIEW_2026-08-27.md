# C3-02 Through C3-05 Branch-Tip Review

Date: 2026-08-27
Reviewed tip: `2370fe26183068cf48bd20474d0bbc9eda6db7a4`
Parent implementation commit: `ab0ce83`
Merge base with reviewed `main@123a105`: `3f31e025941f149d020ff8da68cc2ff12b7d6155`

Status: **not promotable; reconstruction design requires review before code is
written**.

This is a review of the branch tip, not merely the parent implementation
commit. The corrective tip commit is treated as a map of fragile areas and its
claims are re-verified below.

## Executive finding

The branch demonstrates useful API-shape experiments and its ordinary,
AddressSanitizer, and ThreadSanitizer test runs pass. It does not meet the
documented C3-02 through C3-05 merge gates, and the tip fix leaves contract and
boundary defects uncovered by its tests.

The branch must not be merged or cherry-picked as a unit. Reconstruction should
reuse reviewed intent and algorithms where they survive the gates, while an
explicit divergence ledger accounts for every departure from the tip.

The sanitizer passes apply only to existing test coverage. There is no
non-unit-stride test, no fixed hash byte vector, no profile larger than 256
blocks, no 32-bit ABI layout run, and no concurrent queue-capacity test.

An independent linked-C probe on arm64 measured:

```text
sizeof(cyrinx_status_t)             = 4
sizeof(cyrinx_abi_header_t)         = 16
sizeof(cyrinx_profile_t)            = 136
sizeof(cyrinx_batch_input_layout_t) = 72
sizeof(cyrinx_batch_result_t)       = 384
```

The status enum happens to be four bytes on this compiler. C does not guarantee
that width, so this observation does not satisfy the fixed-width contract.

The five registered profiles report 75, 75, 107, 169, and 134 blocks. The
more-than-256-block write fix is therefore not reached by any registered-profile
test.

## Blocking findings

### C3-02 — CI baseline

1. The workflow installs the current Homebrew formatter and linter versions
   instead of enforcing repository-pinned versions. A future package update can
   change the gate without a repository diff.
2. It omits the claims gate, vendored-source integrity gate, API inventory,
   SwiftLint-baseline verification, portable C tests, documentation link check,
   separate coverage observation, warning artifact, research `.venv` job, and
   the exact Swift and Android chat commands.
3. It builds the older Android HIL target but does not reconcile the existing
   chat workflow or its JDK/toolchain requirements.
4. The workflow cannot pass its own format and lint steps at the reviewed tip.

Conclusion: rebuild C3-02 after the claims, format-ownership, and lint-baseline
PRs merge. Do not copy the branch workflow.

### C3-03 — versioned C ABI foundation

1. `cyrinx_status_t` is a C enum, not an `int32_t`. Retained structure sizes and
   counts use `size_t`, contrary to the roadmap's fixed-width status/count
   requirement and producing architecture-dependent layouts.
2. `CYRINX_API` is defined independently in several headers. The Windows build
   condition differs: profiles use `CCYRINX_EXPORTS`, while batch uses
   `CYRINX_BUILD`.
3. The declared prefix-compatibility model is internally inconsistent.
   Validation requires `struct_size >= sizeof(current_type)`, so an older known
   prefix is rejected. Profile lookup then claims to copy a caller-sized prefix,
   but the validator has already required the complete current structure.
4. ABI tests assert lower bounds such as `size >= 16` rather than exact sizes,
   offsets, alignment, and architecture-specific fixtures. There is no 32-bit
   Android layout result and no existing-2.x consumer fixture.
5. A test-only public type and constant are shipped in `cyrinx_base.h`.
6. Allocator, clock, lifecycle, ownership, thread affinity, callback lifetime,
   allocator-failure behavior, and error precedence are largely comments and
   typedefs; the claimed cases are not exercised by a retained object.

Conclusion: the header is a useful sketch, not a promotable ABI foundation.

### C3-04 — profile registry and identity

1. The registry exists only as hand-written C constants plus a Swift wrapper.
   Kotlin/JNI, benchmark manifests, and documentation are not generated from or
   proved against one canonical source, so the C3-04 merge gate is unmet.
2. The nominal 32-byte content hash is an eight-byte FNV-1a value followed by
   24 zero bytes. It has neither the representation nor collision properties a
   reader would reasonably infer from a 32-byte hash field.
3. The hash excludes profile ID, classification, and block count. Changing a
   profile from experimental to qualified does not invalidate its hash. Whether
   evidence classification is mutable metadata or identity-bound is not
   specified.
4. The endian fix serializes integer and double bit patterns as big-endian, but
   tests prove only self-consistency on one host. No fixed canonical byte stream
   or expected hash vector would fail if serialization changed again.
5. `cyrinx_profile_compute_hash` does not validate the ABI header before reading
   the complete structure. Range validation does not explicitly reject every
   non-finite double or every conversion that exceeds the downstream `int`
   range.
6. The branch labels two device-specific profiles as qualified without making
   route/evidence identity part of the registry contract. This conflicts with
   the repository's narrower evidence classifications.

Conclusion: decide the identity schema and evidence boundary before freezing
IDs or hashes.

### C3-05 — batch capture and result contract

1. The tip's interleaved-frame correction is off by one. With a single exact
   stereo buffer containing `2N` samples, offset 1, and stride 2, it computes
   `(2N - 1) / 2`, which is `N - 1`. The last complete frame is omitted and
   consumed-sample accounting is consequently short.
2. Separate primary and secondary buffers share one stride. The API cannot
   describe independent strides or offsets, and there is no explicit channel
   order despite the C3-05 scope requiring one.
3. Raw `primary_count >= frame_samples` is checked before converting through
   stride. The resulting available frame count can still be shorter than a
   frame. Zero-frame allocation is reported as an internal error on platforms
   where `malloc(0)` returns null rather than as malformed input.
4. Batch encode and decode validate only the profile ABI header, not the profile
   hash, block count, or complete profile contract. A modified profile carrying
   a stale hash can be processed and that stale identity is copied into the
   result.
5. The 256-byte block-validity array prevents the result from identifying every
   block for an otherwise-valid profile with more than 256 blocks. The tip fix
   prevents an encode overflow by truncating the mask; it does not satisfy the
   ordered-completeness merge gate. Profile validation does not impose a 256
   block maximum.
6. `monotonic_start_index` and `discontinuity_flags` are accepted but ignored.
   `propagation_delay_ms` and `symbol_timing_error` are always reported as zero,
   so their current meaning is placeholder rather than measured evidence.
7. The tests do not compare the batch contract with the frozen Python oracle,
   JNI, retained captures, malformed channel order, partial block recovery, or
   declared per-field tolerances.
8. The Swift wrapper added in the same branch is beyond C3-05 and is not a
   lossless future-value binding. The branch's TSAN fix replaces runtime-session
   behavior with a timer-driven simulation that ignores payload and send
   options and always succeeds. This is a semantic rewrite, not a generally
   acceptable synchronization correction.
9. The Swift queue capacity check and insertion are separate lock operations.
   Concurrent callers can all observe capacity and then exceed the 16-transfer
   bound even though TSAN reports no data race.

Conclusion: retain the coarse-grained batch concept, but redesign the layout,
result capacity negotiation, validation, and evidence semantics before coding.

## Reconstruction proposal for critique

No implementation should start until this contract proposal is accepted or
amended.

### Change A — C3-02 reproducible CI

- Build on the merged claims, vendor-integrity, format-selection, lint-baseline,
  and API-inventory scripts.
- Pin Xcode/Swift, SwiftLint, swift-format, clang-format, ShellCheck, JDK, Gradle,
  Android SDK/NDK, and any CMake/Ninja versions used by the gate.
- Run the exact root, Swift chat package, Apple chat app, Android chat, Android
  HIL, portable C, C/C++ header, documentation, and research commands.
- Store compiler warnings, separate Swift/C coverage observations, sanitizer
  logs, and version manifests as artifacts. Do not block on historical coverage
  or warning counts until their baselines are explicit.

### Change B — C3-03 ABI foundation

- Define status storage as `int32_t`; define symbolic status constants
  separately from storage width.
- Use a single export macro from the base header and one build-definition name.
- Use `uint32_t struct_size` plus `uint32_t abi_version` as the common prefix.
  Define a named minimum readable/writable prefix for each version rather than
  treating the current `sizeof` as the minimum forever.
- Use fixed-width counts in retained structures. Convert to `size_t` only after
  checked bounds at implementation boundaries.
- Keep test fixtures out of public production headers.
- Add exact size, alignment, and offset fixtures for each supported Apple and
  Android ABI; compile C and C++ consumers with hidden visibility; retain a 2.x
  consumer binary/source fixture.
- Prove no partial output on validation failure and document error precedence,
  callback lifetime, allocator ownership, and thread affinity with at least one
  real opaque object exercising allocation failure and teardown.

### Change C — C3-04 canonical profiles

- Check in one machine-readable canonical registry and deterministically
  generate or verify C, Swift, Kotlin/JNI, benchmark, and documentation views.
- Define a versioned, domain-separated canonical byte serialization with a
  checked-in byte vector for every profile.
- If the field remains 32 bytes, use SHA-256 through a reviewed portable
  implementation. If FNV-1a64 is intentionally retained, expose it truthfully
  as a 64-bit non-cryptographic fingerprint instead of zero-padding it.
- Decide explicitly whether evidence classification and route qualification are
  identity-bound. The recommendation is to keep physical/wire parameters in
  profile identity and store evidence qualification in a separate, versioned
  evidence manifest so new evidence does not change wire identity.
- Reject non-finite values, overflow-prone dimensions, invalid Nyquist/band
  relationships, geometry mismatch, duplicate IDs, duplicate identities, and
  unsupported enum values before hashing or use.

### Change D — C3-05 batch contract

- Represent each input channel as an explicit strided view with its own pointer,
  raw sample count, offset, stride, and role. Mono, planar stereo, and
  interleaved stereo then use the same checked frame-count formula.
- Distinguish raw storage samples, logical channel frames, and monotonic frame
  indices in field names and result accounting.
- Replace the embedded 256-byte validity array with caller-provided validity
  storage plus capacity/required-count negotiation, or impose and validate a
  documented maximum before processing. Caller-provided storage is preferred.
- Fully validate the profile before encoding or decoding. Check all additions,
  multiplications, pointer offsets, fixed-width-to-`size_t` conversions, and
  evidence-counter saturation.
- Either compute timing fields and honor discontinuity metadata or remove those
  fields from version 1. Placeholders must not be represented as measurements.
- Specify error precedence and which capacity fields may be written on
  `BUFFER_TOO_SMALL`; all other rejected calls leave output unchanged.
- Add fixed vectors and malformed cases for exact/odd interleaved lengths,
  independent strides, swapped roles, aliased channels, zero/one sample,
  unequal lengths, more than 256 blocks, stale hashes, truncation, non-finite
  input, partial recovery, and consumed/produced ranges.

The branch's `Cyrinx3API.swift` and its tests are excluded from Changes A-D.
Swift value binding belongs to C3-06 after the C result is accepted. Runtime
session behavior must not be replaced by an always-successful simulator as an
incidental race fix.

## Expected divergence ledger

Patch identity with the tip is neither possible nor desirable after this
review. The eventual checked-in ledger must enumerate exact hunks, but the
following divergence classes are already expected:

| Tip content | Reconstruction disposition | Reason |
|---|---|---|
| `.github/workflows/ci.yml` | Replace | Unpinned and incomplete relative to current gates. |
| KISS FFT formatting | Drop | Vendored bytes are protected by upstream integrity. |
| Formatting-only existing C changes | Drop | Mechanical formatting is isolated in its own PR. |
| Stale roadmap, plan, API inventory, testing, and ADR documents | Reconcile or drop | Current `main` has newer ledgers and decisions. |
| `cyrinx_base.h` layout and test type | Redesign | Fixed-width and public-header blockers. |
| profile hash and hand-copied registry | Redesign | Identity and canonical-source blockers. |
| batch input/result structures | Redesign | Stride, mask-capacity, and evidence blockers. |
| `Cyrinx3API.swift` and mock-session race fix | Defer to C3-06 or separate simulator work | Out of tranche scope and semantic divergence. |
| Ordinary/hash/batch tests | Reuse selectively and extend | Current tests cover useful happy paths but not promotion gates. |

Every final divergence needs its reconstructed commit, reason, validation
impact, and reviewer disposition. An unlisted hunk remains a merge blocker.

## Review decisions required

1. Approve `uint32_t` for ABI prefix fields and fixed-width retained counts, or
   specify a different cross-architecture representation.
2. Approve SHA-256 for the 32-byte profile identity, or explicitly choose a
   smaller non-cryptographic fingerprint and rename/resize the field.
3. Confirm that route/evidence qualification is separate from immutable wire
   profile identity.
4. Approve caller-provided block-validity storage rather than a fixed embedded
   maximum.
5. Confirm that the Swift message/session facade is deferred to C3-06 and is not
   part of reconstructing C3-02 through C3-05.

Until those decisions are recorded, Phase 3 remains at the review checkpoint.
